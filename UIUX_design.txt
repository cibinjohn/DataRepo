CONCEPT B — Investigation Workspace

An IDE/debugger for failures. Optimized for: deep debugging, log exploration, RCA validation. Primary persona: Data Engineer / Platform Engineer doing the actual fix.

Mental model: Splunk search × Grafana Explore × VS Code. Three persistent panes; you drill in place instead of hopping pages.

B1. Information Architecture

DataOps Assistant — Workspace
├── Workspace Home   (recent + pinned investigations, failure inbox)
├── Failure Inbox    (list)
├── Investigation Workspace   (3-pane, the core)
│   ├── LEFT   task navigator + execution timeline
│   ├── CENTER evidence tabs: Logs · Stack Trace · Signals · Diff
│   └── RIGHT  RCA panel + validation controls
├── RCA Report       (full-page reading / export view)
└── Historical Explorer  (cohort comparison)

B2. User Flow

Failure Inbox ─► open in Workspace
        │
        ▼  LEFT: pick failed task + attempt
  ┌─────────────────────────────────────────────┐
  │ CENTER: read log ⇄ stack trace ⇄ signals ⇄  │  ← raw evidence, searchable
  │         diff vs last good run                │
  └─────────────────────────────────────────────┘
        │  RIGHT: AI RCA claims, each with "jump to evidence"
        ▼
  Validate: ✓ confirm / ✎ edit / ✗ reject each finding (human-in-loop)
        │
        ▼
  Finalize RCA Report ─► export   |   "compare cohort" ─► Historical Explorer

B4. Screen layout logic

Three resizable panes; left = what failed, center = the evidence, right = the claim. Critically, the AI sits on the right, subordinate to evidence in the center — the layout physically encodes "verify, then trust." Each AI claim links into the center pane (jump-to-line). Diff-vs-last-good is a first-class tab because "what changed?" is the debugger's first question.

B5. Navigation

Tab-within-pane (Logs/Stack/Signals/Diff) replaces page navigation for the core loop — you stay in the workspace. Top-level rail only for Home · Inbox · Historical. Resolved investigations become read-only RCA reports.

B6. UX rationale

Engineers fixing the actual bug live in logs and stack traces. Page-hopping breaks debugging flow, so the workspace keeps navigator + evidence + claim co-visible. The validation controls (✓/✎/✗ per claim) make the human the decision-maker and create an audit trail — essential for trusting LLM output and for post-incident review.

B7. Streamlit components


3-pane: st.columns([1,3,2]) inside st.container(border=True); persist pane state in st.session_state.
Logs / stack: st.code(log, line_numbers=True, wrap_lines=True, height=…); for search/scroll use streamlit-ace or a custom search box filtering lines.
Evidence tabs: st.tabs(["Logs","Stack","Signals","Diff"]).
Timeline: Plotly Gantt (px.timeline) from start_time/end_time → st.plotly_chart.
Per-claim validation: st.session_state + buttons / st.feedback; st.data_editor for editable claim list.
Diff: render unified diff in st.code(language="diff").
Jump-to-evidence: anchor via st.session_state + st.scroll_to pattern / highlight.
Live status while RCA generates: st.status + st.write_stream.


B8. Pros / Cons

Pros: best-in-class for real debugging and RCA validation; evidence-first layout builds trust; audit trail; "what changed" front and center. Cons: denser, steeper learning curve; overkill for a quick triage glance; 3-pane is cramped on small screens; more custom components (ace, Plotly Gantt) = more build effort.
